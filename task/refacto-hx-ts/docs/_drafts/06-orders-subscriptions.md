# 06 - Orders, subscriptions (CSA contracts), baskets, order UI

Documents what the code does today. All paths are relative to the repo root `camap-docker/`.
"unverified" = not confirmed by reading code in the scanned scope.
Abbreviations used in refs: `SS` = `camap-hx/src/service/SubscriptionService.hx`, `OS` = `camap-hx/src/service/OrderService.hx` (always followed by line numbers; the full path is given at first use in each section).

## 1. Overview

- Every order line (`UserOrder`) must belong to a `Subscription`: `OrderService.make` throws `"Impossible d'enregistrer une commande sans souscription."` when no subscription is passed (camap-hx/src/service/OrderService.hx:109). A subscription is (user, optional user2, catalog, startDate, endDate, `defaultOrders` JSON, `absentDistribIds` CSV) (camap-hx/src/db/Subscription.hx:9-18).
- Two catalog types: `TYPE_CONSTORDERS = 0` (classic AMAP, same order each distribution) and `TYPE_VARORDER = 1` (variable) (camap-hx/src/db/Catalog.hx:53-54).
- Basket = one row per (user, MultiDistrib), groups the UserOrders of all catalogs of that distribution day; `num` = sequence number inside the MultiDistrib (camap-hx/src/db/Basket.hx:15-27, 48-66).
- The whole write path (subscriptions, orders, baskets) lives in Haxe (`camap-hx`). The TS side (`camap-ts`) has **no mutation** for subscriptions/orders/baskets (grep of `@Mutation` in `camap-ts/packages/api-core/src/{shop,groups,vendors,payments}` finds none touching them); it only has entities, read-only GraphQL fields, and the React front (`csaCatalog`, `batchOrder`) which calls the Haxe REST API (`/api/subscription/*`, `/api/catalog/*`) via `camap-ts/packages/front-core/src/modules/csaCatalog/requests.tsx:1-162` (base URL = `CAMAP_HOST + "/api"`, camap-ts/packages/front-core/src/lib/REST/useRestGetApi.ts:4-5).
- There is no "renewal" feature in either code base: grep for renew/reconduct finds only memberships (camap-ts/packages/api-core/src/groups/services/memberships.service.ts) and `ContractAdmin.doDuplicate`, which copies the catalog (and optionally products/distributions) but not subscriptions (camap-hx/src/controller/ContractAdmin.hx:782-900; no `Subscription` reference in that range). A new season = new catalog + new subscriptions.
- Member-facing subscription/order UI = Neo module `csaCatalog` (TS) hosted by the Haxe template `contract/order.mtt` at `/subscriptions/contract/:catalogId` (camap-hx/lang/master/tpl/contract/order.mtt:14-21; camap-hx/src/controller/Subscriptions.hx:22-30). Admin batch ordering = Neo module `batchOrder` hosted by `contractadmin/batchOrder.mtt` (camap-hx/lang/master/tpl/contractadmin/batchOrder.mtt:5; camap-hx/src/controller/ContractAdmin.hx:1102-1108), which reuses `CsaCatalogRouter` with `adminMode` (camap-ts/packages/front-core/src/modules/batchOrder/BatchOrder.module.tsx:158-167).
- A legacy Haxe-React `OrderBox` dialog (`camap-hx/js/react/order/**`) is still used by the back-office order pages `contractadmin/orders.mtt` and `ordersByDate.mtt` (`_Camap.initOrderBox(...)`, camap-hx/lang/master/tpl/contractadmin/orders.mtt:29,107; ordersByDate.mtt:66) and talks to `/api/order/*`.

## 3. Business rules

Numbered; "HX" refs are Haxe, "TS" refs are TypeScript.

### 3.1 Vocabulary / data

R1. Subscription date bounds: on create/update `startDate` is normalised to 00:00:00 and `endDate` to 23:59:59 of the given day (camap-hx/src/service/SubscriptionService.hx:666-667, 787-788). Both must lie inside the catalog dates (catalog start 00:00:00 .. catalog end 23:59:59): start `>= catalogStart && < catalogEnd`, end `> catalogStart && <= catalogEnd` (SubscriptionService.hx:405-415). Start must be strictly before end (373-375).
R2. A subscription's distributions = distributions of the catalog with `date >= startDate && end <= endDate`, minus the absence distributions when the catalog has absence management (SubscriptionService.hx:192-225). "open" variant adds `orderStartDate <= now < orderEndDate` (202-208); "past" adds `end <= end of today` (209-214).
R3. `Catalog.hasAbsencesManagement()` and `hasDefaultOrdersManagement()` are true for CONST catalogs and for VAR catalogs with `distribMinOrdersTotal > 0`; absences additionally need `absentDistribsMaxNb > 0` and both absence dates (camap-hx/src/db/Catalog.hx:145-160). `hasConstraints()` = VAR with `distribMinOrdersTotal > 0 || catalogMinOrdersTotal > 0` (Catalog.hx:141-143).

### 3.2 Constant vs variable orders

R4. CONST: the "default order" (list of `{productId, quantity, userId2?, invertSharedOrder?}`) is the subscription's recurrent order; `createRecurrentOrders` materialises one `UserOrder` per product per distribution of the subscription (camap-hx/src/service/SubscriptionService.hx:899-965). Distributions that carry `quantities > 1` (another distribution merged into it) get the order created `quantities` times (947-949); `make` accumulates same user/product/distribution into one row (OS:90-97), so the row quantity is multiplied (multiWeight products stay separate rows, OS:52-65, 90).
R5. VAR: orders are per distribution. Default order exists only if `distribMinOrdersTotal > 0` (R3). It is stored in `Subscription.defaultOrders` (SubscriptionService.hx:1010) and `createRecurrentOrders` creates it on every subscription distribution whose `orderEndDate` is not past (`orderEndDate < now` -> skipped, 922-925). Existing non-closed orders of the subscription are deleted first (906-916), so **re-saving the default order overwrites manual per-distribution edits on all not-yet-closed distributions**; closed distributions are untouched for VAR.
R6. For a CONST subscription all orders (including past ones) are deleted and recreated at the **current** `product.price` (SubscriptionService.hx:909 only exempts VAR; `OrderService.make` sets `productPrice = product.price`, OS:77). Non-admin cannot do it once there are past orders: `updateDefaultOrders` throws `PastOrders` when `hasPastDistribOrders && !adminMode` (SubscriptionService.hx:989-993). The admin edit form always re-saves orders when the catalog has default-order management (SubscriptionAdmin.hx:223-272 then `updateSubscription` -> `updateDefaultOrders`, SubscriptionService.hx:802-804).
R7. VAR without minimums (`distribMinOrdersTotal == 0 && catalogMinOrdersTotal == 0`): no default order; the TS wizard skips the "required orders" step (camap-ts/packages/front-core/src/modules/csaCatalog/CsaCatalogRouter.tsx:101-108) and `checkDefaultOrder` returns true immediately (camap-hx/src/controller/api/Subscription.hx:122-124).
R8. VAR + `distribMinOrdersTotal > 0`: a cron applies the default order to subscriptions that have **no order at all** on a distribution whose `orderEndDate` fell in the last hour, unless the distribution is an absence (camap-hx/src/controller/Cron.hx:227-278); it creates orders with `OrderService.make` and an in-app notification, then refreshes the total operation. A `make` error (e.g. stock) is not caught per subscription there (unverified effect on the rest of the loop).
R9. Shared (alternating) baskets: only CONST. `createSubscription` takes `user2` from the order lines (`checkUser2`: only one distinct `userId2` allowed, SubscriptionService.hx:759-772, 669-673); `updateSubscription` only overwrites `user2` when a non-null user2 is passed, i.e. it can never be cleared there (790-796). `UserOrder.getWhosTurn` = parity of the count of catalog distributions from `catalog.startDate` to the distribution date (not from subscription start), flipped by flag `InvertSharedOrder` (camap-hx/src/db/UserOrder.hx:63-74). The TS front never sends `userId2` (camap-ts/packages/front-core/src/modules/csaCatalog/requests.tsx:57-69, `RestCsaDefaultOrder` in interfaces.ts:119-122), so alternating baskets can only be set from the Haxe admin form (SubscriptionAdmin.hx:109-137). `Distribution.getUserOrders` includes `user2` orders for CONST catalogs only (camap-hx/src/db/Distribution.hx:94-100).

### 3.3 Subscription lifecycle

Create (`SubscriptionService.createSubscription`, camap-hx/src/service/SubscriptionService.hx:644-703):
R10. Start defaults to the date of the next not-closed distribution (`getComingOpenDistrib`, 152-159, 630-638; for VAR it needs `orderStartDate <= now < orderEndDate`, for CONST only `orderEndDate > now`); end defaults to catalog end (647-653). The TS REST client never sends dates, so members (and the batch admin) always get "from next open distribution to catalog end"; only the Haxe admin form lets dates be chosen (SubscriptionAdmin.hx:73-100, 159).
R11. If the user is not a member of the catalog's group: auto-joined when `group.regOption == Open`, otherwise error (SubscriptionService.hx:654-661).
R12. Absences: explicit ids or `absenceNb` automatic selection are applied before validation (675-682) with `adminMode=false` hard-coded in the call (details in the absences draft).
R13. `checkSubscriptionBeforeUpdate` (360-479): (a) catalog must `hasOpenOrders()` unless `adminMode` (363) - `hasOpenOrders` = `UsersCanOrder` flag + inside catalog dates (+ for VAR at least one distribution currently inside its order window, camap-hx/src/db/Catalog.hx:116-125); (b) catalog must have at least one non-old distribution (367-370); (c) R1 date checks; (d) non-admin: start >= next open distribution date, and for edits only if the start date was changed into the past-but-not-yet-started zone (377-400); (e) no overlap with another subscription of the same user **and same catalog** (three range queries, 417-466) -> `OverlappingSubscription`; (f) existing VAR sub: the new range may not exclude past orders (`hasPastDistribOrdersOutsideSubscription`, 468-473) -> `PastOrders`; (g) non-admin: for CONST, no past distribution without an order in the range (`hasPastDistribsWithoutOrders`, 475-478, 874-888; VAR deliberately not blocked, comment 878-879) -> `PastDistributionsWithoutOrders`.
R14. After `insert`: default orders (if `hasDefaultOrdersManagement`, 687-690) are generated, then `initialOrders` (explicit per-distribution quantities, used by VAR with a contract-wide minimum) are applied on top (691-694), `SubscriptionTotal` operation created, `areVarOrdersValid` run (696-697), "subscription created" notification mails queued (699-701, 705-757), user balance updated (701).
R15. REST create (`/api/subscription`) always runs with `adminMode = true` (camap-hx/src/controller/api/Subscription.hx:50). So the checks (a), (d), (g) of R13 are bypassed on this path; the compensating guards are the explicit `hasOpenOrders` test for non-managers (45-47) and the fact that start date is always computed (R10).
Update (`updateSubscription`, SubscriptionService.hx:778-805): only reachable from the Haxe admin edit form (SubscriptionAdmin.hx:294). Requires both dates; locks, applies R13, updates, then re-creates orders if `hasDefaultOrdersManagement && ordersData != null` (R5/R6). The admin form refuses an absence date outside the new subscription period (SubscriptionAdmin.hx:283-292).
Delete (`deleteSubscription`, SubscriptionService.hx:814-838): refused when there are orders with `quantity > 0` on past distributions (`hasPastDistribOrders`, 817-819, 843-855; "past" = `end <= end of today`) or when any `Payment` operation exists on the subscription (822-824; note balance transfers are `Payment` operations, 1112, 1123); otherwise deletes all orders (`OrderService.delete(order, true)`), all operations of the subscription, updates balance, deletes the subscription. Members can delete only their own (Subscriptions.hx:36), admins via token-protected route (SubscriptionAdmin.hx:47-61).
R16. Renewal: none (see Overview). `getCurrentOrComingSubscription` returns the single subscription of the user for the catalog with `endDate >= (next open distribution date or now)` (SubscriptionService.hx:176-180) and is what `/subscriptions/contract/:id` opens.
R17. Balance transfer: moves `balance` from one subscription to another of the **same user** by creating two `Payment` operations of payment type `transfer`; negative balances can be transferred (camap-hx/src/service/SubscriptionService.hx:1099-1139). The controller lists targets = other not-closed (`endDate >= now`) subscriptions of the same user and same vendor (SubscriptionService.hx:118-127) but does not re-validate the selected id against that list (SubscriptionAdmin.hx:398-403).

### 3.4 Minimums / constraints

R18. `distribMinOrdersTotal` (VAR): every not-yet-closed distribution (`orderEndDate >= now`) in the submitted orders must total at least that amount; each line is `roundTo(quantity * productPrice, 2)`; closed distributions are skipped so that admin-modified past orders never block (camap-hx/src/service/SubscriptionService.hx:581-602). Error type `CatalogRequirementsNotMet`.
R19. `catalogMinOrdersTotal` (VAR, whole contract): required total = `floor(ratio * catalogMinOrdersTotal)` with `ratio = subscription distributions (absences excluded) / all catalog distributions`; without a subscription (pre-check), the numerator is "distributions with date >= next open distribution date" (SubscriptionService.hx:485-515). The sum includes all orders of the subscription (closed ones too) (604-622). `areVarOrdersValid` throws `"Aucune commande dans cette souscription"` when constraints exist and the subscription has zero orders (555-559). It is invoked at create (697), `updateOrders` (1018), and `updateDefaultOrders` for VAR (999-1001). The TS front re-implements the pre-check client-side (`minSubscriptionOrder`, camap-ts/packages/front-core/src/modules/csaCatalog/CsaCatalog.context.tsx:286-290: `floor(catalogMin / distributions.length * remainingDistributions)`), and disables "save" if `distribMinOrdersTotal > total` or `minSubscriptionOrder > contractTotal` (camap-ts/packages/front-core/src/modules/csaCatalog/containers/CsaCatalogOrdersMobile.tsx:297-341, 352-373).
R20. Absences interact: absent distributions are excluded from `getSubscriptionDistributions` (R2), from the ratio of R19, and from the cron (R8); absence update re-creates/removes orders (camap-hx/src/service/AbsencesService.hx:114-190, documented elsewhere).

### 3.5 Order creation / edit rules

R21. `OrderService.make` (camap-hx/src/service/OrderService.hx:30-139): rejects null distribution/quantity, negative quantity, disabled vendor; non-integer quantity unless `canHaveFloatQt(product)` (= `variablePrice || bulk`, 19-21, 44-48; integer test = `FloatTool.isInt` i.e. equal after `round(x*10000)`, camap-hx/src/tools/FloatTool.hx:9-16); `multiWeight` with quantity > 1 splits into N rows of quantity 1 and requires an integer (52-65); quantity 0 returns null (68); `productPrice` snapshot = `product.price` (77); `feesRate` only if `hasPercentageOnOrders()` which is hard-coded `false` (78-80; Catalog.hx:128-131), so `feesRate` is effectively always 0; same user+product+distribution rows are merged and the previous rows deleted (71, 90-97); basket = given or `Basket.getOrCreate(user, multiDistrib)` (100-103); subscription is mandatory (108-109).
R22. Stock (when catalog has `StockManagement` and `product.stock != null`): after insert, available stock is `getAvailableStock(distribId, ignoreOrderId)`; stock 0 -> quantity set to 0 and error; insufficient -> quantity clamped to available and an error is still thrown (OS:116-135). multiWeight counts as 1 unit regardless of weight (OS:121). Stock = distribution (or global) stock minus sum of existing orders with `quantity>0` (camap-hx/src/db/Product.hx:147-179). `assertStocksAvailable` is the pre-check used by `checkDefaultOrder` (OS:141-160).
R23. `OrderService.edit` (OS:166-240): negative refused; non-integer refused for non-float products; `paid` reset to false when quantity increases unless `paid` given (183-187); `user2`/invert flags overwritten (user2 reset to null when not passed, 190-197); stock check (199-222); quantity 0 keeps the row with `quantity=0, paid=true` (225-228) (UI label "Canceled", OS:366-367). `editMultiWeight` adjusts the number of rows (create/zero) from a single integer input (OS:245-293). `delete` only when quantity is 0 or `force` (OS:298-325); it refreshes the `SubscriptionTotal` operation.
R24. `canModify` for the UI: VAR -> now strictly inside the distribution's order window (or `orderStartDate == null`), CONST -> `catalog.isUserOrderAvailable()`; and never when `paid` (camap-hx/src/db/UserOrder.hx:89-107). Window of a distribution: `Distribution.canOrderNow()` = `UsersCanOrder` flag && `orderStartDate < now < orderEndDate` (camap-hx/src/db/Distribution.hx:154-165).
R25. **Server-side window enforcement is partial**: `OrderService.make/edit` and `SubscriptionService.setOrders` do not test the distribution order window; the REST `updateOrders` only requires the catalog to have *some* open distribution for non-managers (camap-hx/src/controller/api/Subscription.hx:70-73, camap-hx/src/service/SubscriptionService.hx:1021-1056). The window is enforced by the TS UI (distribution `state` Open/NotYetOpen/Closed/Absent from `orderStartDate/orderEndDate`, camap-ts/packages/front-core/src/modules/csaCatalog/interfaces.ts:77-100) and by `Contract.doEditVarOrders` (Contract.hx:229). Whether another layer (event listeners on `MakeOrder`) enforces it is unverified.
R26. ## 4. Flows

### 4.1 Member creates a subscription (TS UI -> Haxe API)
1. Home/list links to `/subscriptions/contract/:id` (camap-hx/lang/master/tpl/home.mtt:80,156; macros.mtt:269) -> Neo `csaCatalog` with current/coming subscription id.
2. TS loads `GET /api/catalog/:id`, stocks, then (if sub) `GET /api/subscription/:id` (camap-ts/packages/front-core/src/modules/csaCatalog/CsaCatalog.context.tsx:112-141).
3. Wizard `presentation -> absences (if absentDistribsMaxNb>0) -> requiredOrders (if CONST or any minimum) -> create` (CsaCatalogRouter.tsx:91-136). Optional `POST /api/subscription/checkDefaultOrder/:catalog` is available (requests.tsx:156-162).
4. `POST /api/subscription` `{userId, catalogId, defaultOrder, absentDistribIds, initialOrders}` -> permission checks (Subscription.hx:35-47) -> `createSubscription` (R10-R15) -> JSON DTO (`distributions` with orders merged for multiWeight, `constraints`, `totalOrdered`, `balance`, `minSubscriptionOrder`, Subscription.hx:149-203).
5. Review step: CONST -> `POST updateDefaultOrder` (CsaCatalogRouter.tsx:145-152); VAR -> `POST updateOrders` with the modified distributions (153-180).

### 4.2 Admin orders for a member
- Admin "batch order" page: member `Select` + the same `CsaCatalogRouter` with `adminMode` (BatchOrder.module.tsx:119-167). The member's subscription = first one with `endDate >= now` (72-77). With no subscription an admin sees a "create subscription" button which uses the same REST create (CsaCatalogRouter.tsx:212-231).
- Back-office "orders" page (`/contractAdmin/orders/:catalog?d=`): OrderBox dialog (`/api/order/get|update`) or inline qty inputs (`/api/order/updateOrderQuantity`).
- Admin form `/contractAdmin/subscriptions/insert|edit` (Haxe forms) is the only place to choose dates, `user2`/invert, and to edit a CONST subscription's recurrent order with admin privileges.

### 4.3 Deletion
Member: GET `/subscriptions/delete/:id` (owner, no token) -> `deleteSubscription`; admin: tokenised GET `/contractAdmin/subscriptions/delete/:id`. Both rely on the `deleteSubscription` guards of section 3.3.

### 4.4 Default order cron (VAR with `distribMinOrdersTotal > 0`)
Hourly: distributions whose `orderEndDate` fell in the last hour -> subscriptions covering the distribution date, not absent, with no order for that distribution -> `OrderService.make` for each default-order line -> notification mail `DEFAULT_ORDER(catalogId)` -> `createOrUpdateTotalOperation` (camap-hx/src/controller/Cron.hx:227-278).
